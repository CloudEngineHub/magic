# 纯客户端超大 PPTX 导出方案

**日期：** 2026-07-30
**状态：** 待评审
**目标读者：** 产品、架构、前端及客户端研发

## 1. 背景与目标

业务需要在没有后端参与的情况下，导出约 300 页的单个 PPTX。文件可能包含大量图片、视频、音频和图表，最终体积可能达到数 GB、十几 GB，甚至更大。

目标如下：

- 完全在客户端完成，不新增导出后端。
- 产品不设置 1GB、4GB、10GB 等固定总容量上限。
- 低性能设备能够完成多 GB 文件导出。
- 用户只点击一次，选择保存位置后自动完成。
- 最终生成一个标准 PPTX，不分卷。

“无固定产品容量上限”不等于物理无限。实际容量仍取决于本地磁盘、文件系统、浏览器或客户端能力、单个媒体处理方式，以及 PowerPoint 对超大文件的兼容性。

## 2. 核心结论

该目标可以纯客户端实现，但必须放弃“全部内容留在内存，最后一次性生成 Blob”的现有方式，改成真正的流式导出。

```text
用户选择保存位置
        ↓
页面逐页准备
        ↓
媒体按二进制流读取
        ↓
PptxGenJS 逐页写入并释放
        ↓
zip.js 生成 ZIP32 / ZIP64
        ↓
直接写入本地文件
```

内存只保存当前页、当前媒体分块和少量 ZIP 元数据，不能随最终文件大小线性增长。

## 3. 预期收益

### 建议对外口径

> 典型 200 页图文 PPT，整体导出耗时预计下降约 20%；图片、视频越多，媒体打包收益越明显。多 GB 场景的第一目标是从容易内存溢出变为能够稳定完成。

内部目标建议定为：典型 200 页图文场景总耗时下降 25%～35%，发布验收下限为 20%；媒体打包阶段耗时下降至少 60%，挑战目标为 75%。

| 200 页场景 | 总耗时预计下降 | 说明 |
|---|---:|---|
| 纯文字、小文件 | 0～10% | 页面渲染占主要时间，流式打包收益有限 |
| 普通图片，约 100～500MB | 20～35% | 取消 base64 和最终完整 Blob 后收益明显 |
| 本地大图片、视频直接透传 | 25～50% | 媒体越大，二进制流式路径收益越高 |
| 网络媒体成为瓶颈 | 10～25% | 总耗时主要受网络速度影响 |
| 图片必须解码、缩放或转格式 | 0～15% | 主要耗时仍在图片处理，不承诺固定提速 |

当前 PptxGenJS 的本地微基准也说明了区别。以下数据只代表“媒体已经准备完成后的打包阶段”，不是完整业务端到端耗时：

| 200 页打包场景 | 当前 JSZip | zip.js 流式原型 | 耗时下降 |
|---|---:|---:|---:|
| 图片型，约 89MB | 3.76 秒 | 0.73 秒 | 约 81% |
| 视频型，约 213MB | 8.73 秒 | 1.27 秒 | 约 85% |

当前代码每页存在 1.5 秒固定等待，200 页仅该等待就至少约 5 分钟。因此，如果只替换 ZIP 引擎，整体耗时预计只能下降约 5%～15%。要达到约 20% 的正式目标，必须同时把固定等待改成事件驱动的页面就绪判断，并保留超时兜底。

除总耗时外，还应验收：

- 固定尺寸一遍流式模式在选择保存位置后 5 秒内开始写盘。
- 普通图片场景峰值内存下降至少 60%，重媒体场景目标下降 70% 以上。
- 纯文字、小文件场景总耗时不得回退超过 5%。
- 当前因 OOM 无法完成的多 GB 场景，不计算提速百分比，按“由不支持变为支持”验收。

所有百分比均表示“总耗时下降”，并在同一设备、同一浏览器、同一数据集和相同缓存条件下比较。

## 4. 为什么当前方案不行

当前链路会把图片和视频读取成完整 ArrayBuffer 或 base64，并长期保留页面、媒体对象和最终 ZIP 结果。文件越大，内存越高，最终可能达到输出体积的数倍。

因此，以下优化只能缓解问题，不能解决问题：

- 把 300 页拆成若干批次。
- 降低图片并发。
- 把 JSZip 放入 Worker。
- 最后把 ArrayBuffer 改成 Blob。

真正需要解决的是：媒体二进制化、页面及时释放，以及 ZIP 结果直接写盘。

## 5. 方案设计

| 改造项 | 方案 |
|---|---|
| 最终输出 | 导出开始时选择保存位置，之后持续写入本地文件，不生成完整 Blob |
| 页面处理 | 每次只准备和提交一页，写完立即释放 DOM、IR 和临时对象 |
| 页面就绪 | 将每页固定等待改为事件驱动判断，仅保留有上限的超时兜底 |
| PptxGenJS | 增加逐页流式会话，旧 API 继续兼容小文件 |
| 媒体输入 | 支持 File、Blob、ReadableStream、OPFS 文件等二进制 Source，不再依赖 base64 |
| ZIP 引擎 | PPTX 外层包和图表内嵌 XLSX 全面统一到 zip.js，迁移后删除 JSZip |
| ZIP64 | 文件可能跨越经典 ZIP 边界时，在开始写入前选择 ZIP64 |
| 媒体处理 | 视频、音频和兼容图片直接 STORE 透传；必须转换的图片单独受内存预算控制 |
| 媒体去重 | 同一媒体被多页引用时，PPTX 中只保存一份 |
| 临时存储 | OPFS 只保存当前暂存资源、页面 IR、转换结果和 ZIP 元数据，不保存完整最终文件 |
| 背压 | Worker 必须等待文件写入完成后再继续，不能无限堆积输出分块 |

### 为什么选择 zip.js

PPTX 本质上是 ZIP 格式的 OOXML 文件，ZIP 无法去掉。zip.js 能够面向 WritableStream 流式写出，并支持 ZIP64；JSZip 继续用于最终打包时，仍容易形成完整内存结果。

统一使用 zip.js 也可以避免小文件和大文件由两套 ZIP 引擎生成，减少兼容差异和维护成本。

## 6. 用户流程

用户不需要在任务完成后再次点击下载：

```text
点击“导出 PPT”
→ 选择文件名和保存位置
→ 系统自动预检、逐页处理、打包和写盘
→ 显示进度
→ 文件关闭成功后提示完成
```

取消、磁盘写满、权限撤销、媒体读取失败或 Worker 异常时，本次导出失败并清理临时数据，不把不完整文件提示为成功。

## 7. 能力边界

| 场景 | 结论 |
|---|---|
| 多个视频累计达到多个 GB | 支持，按分块流式透传 |
| 单个视频超过 4GiB | ZIP64 可生成，仍需验证目标 PowerPoint |
| 大量普通图片 | 支持，逐张处理并及时释放 |
| 单张超大图片无需转换 | 可以直接透传 |
| 单张超大图片必须缩放或转格式 | 受解码内存限制，需要预检、降级或拒绝转换 |
| 浏览器内通用视频转码 | 不支持 |
| 只有 Blob 下载能力 | 只支持受控小文件，不属于多 GB 正式路径 |
| 磁盘空间或文件系统能力不足 | 无法完成，需要明确提示 |

ZIP64 解决的是 ZIP 容器限制，不代表任意 PowerPoint 版本都能流畅打开任意大小的文件。产品应只对经过验证的 Windows/macOS PowerPoint 版本和媒体格式做兼容承诺。

## 8. 实施计划

详细排期、阶段门禁、退出条件和第一周任务见：[执行计划](./2026-07-30-pure-client-large-pptx-export-implementation-plan.md)。

1. **建立基线**：按页面准备、页面渲染、媒体处理、打包、写盘和总耗时分别埋点，固定 200 页测试集。
2. **验证流式 ZIP**：完成 zip.js 文件直写，验证单 entry 和总文件跨 4GiB，以及 8GB、20GB 长时间写入。
3. **改造 PptxGenJS**：增加二进制媒体 Source、逐页提交、媒体去重和 ZIP64 输出，删除 JSZip 运行时。
4. **接入 magic-web**：改为逐页处理和事件驱动页面就绪，加入 Worker 背压、一次点击、进度、取消和清理。
5. **兼容与灰度**：在低性能设备和 Windows/macOS PowerPoint 上验证，再从内部数据逐步扩大到真实业务。

## 9. 验收标准

- 典型 200 页图文场景总耗时下降至少 20%，内部目标为 25%～35%。
- 媒体打包阶段耗时下降至少 60%，挑战目标为 75%。
- 约 300 页、累计多 GB 的 PPTX 可以成功生成。
- 通过跨 4GiB、8GB 和 20GB 长时间测试。
- 代码中不存在固定总媒体大小或总输出大小拒绝线。
- JavaScript Heap 不随输出 GB 数线性增长。
- 大媒体不经过 base64，不生成最终完整 Blob 或 ArrayBuffer。
- 已完成页面可以及时释放。
- 用户只需要一次点击和一次保存位置选择。
- 生成文件可在认证的 PowerPoint Windows/macOS 版本中无修复提示打开。
- 取消、磁盘写满、网络失败和 Worker 异常不会提示假成功。

8GB、20GB 只是认证样本，不是产品容量上限。更大的任务仍使用同一条流式路径，不需要修改容量常量或切换另一套实现。

## 10. 最终建议

建议将以下能力作为一个完整项目实施：

1. PptxGenJS 全面迁移到 zip.js。
2. 新增真正的逐页流式导出 API。
3. 媒体输入改为二进制 Source。
4. 多 GB 文件直接写入用户选择的本地文件。
5. 同时完成 ZIP64、背压、页面释放和媒体去重。

只做分批处理、降低并发或把 JSZip 放进 Worker，仍然无法满足低性能设备导出多个 GB PPTX 的目标。
