# Slide Templates 画布空白区域与循环布局问题

## 状态

- 记录日期：2026-07-14
- 当前处理：暂不修复算法，已恢复到本次改动前的实现
- 影响范围：`SlidesTemplates` 画布的布局、循环渲染、分页加载和可见项查询

## 用户现象

用户持续横向拖动画布时，会反复看到相同模板。部分位置出现空白区域，尤其在缩放画布后更明显。用户期望的行为是：

1. 模板内容不重复循环。
2. 用户向哪个方向移动，就在该方向加载下一页数据。
3. 已有卡片位置保持稳定。
4. 加载区域不应出现内部空洞或无法解释的空白区域。

## 浏览器复现证据

验证页面：`https://www-pre.letsmagic.cn/global/super/slide-templates`

在画布缩放到 60% 后观察到：

### 1. 内部空洞是真实空单元

- 网格单元 `(0, 1)` 为空。
- 当时屏幕范围约为 `x=1035–1222, y=692–797`。
- 空单元中心点 `elementFromPoint(1128.6, 744.4)` 命中画布背景，没有卡片 DOM。
- 左侧卡片为「简约正式咨询方案」，右侧卡片为「技术新人实验手册」。
- 因此该现象不是图片加载失败，也不是虚拟化查询漏掉了 DOM，而是布局本身留下了空单元。

### 2. 内容边界也存在空单元

60% 缩放时，底部边界附近可见 `(x=-4,-3,0,1,2, y=4)` 等空单元。缩放后视口大于当前内容边界，这类边界空白会被放大。

### 3. 黑色精选卡片是独立的加载状态问题

首次截图中的黑色「精选」卡片在等待后图片可以显示；检查结果为：

- 卡片 DOM 已经存在。
- 图片 `complete=true`。
- 图片 `naturalWidth=720`。

这说明黑色区域主要是图片尚未加载或解码时，卡片背景直接显示为 `bg-zinc-900`。它与内部空洞不是同一个根因。

### 4. 可以排除可见项数量截断

在该视口下：

- 实际渲染 41 项。
- 其中 28 个为 `2×2` 精选卡片，13 个为 `1×1` 普通卡片。
- 按当前视口和缩放计算的可见项上限约为 99。

因此空白区域不是 `MAX_VISIBLE_TEMPLATE_CANVAS_ITEMS` 截断造成的。

## 当前原始实现的布局逻辑

恢复后的实现位于：

`src/pages/superMagic/pages/SlidesTemplates/SlidesTemplateCanvasLayoutService.ts`

其关键行为如下：

1. 数据量达到阈值后，使用固定 12 列的循环单元。
2. 新数据按 first-fit 放置到网格中。
3. 为了填满循环单元，会从已加载模板中复制 filler 卡片。
4. `canvasLoop.ts` 根据循环单元坐标生成视口附近的副本。
5. 自动加载会根据循环周期和四个方向尝试请求更多数据。

这套实现能保持循环网格完整，但与「真实数据只出现一次、按用户方向继续加载」的产品要求冲突，是重复模板和后续空白问题的基础原因。

## 本次尝试为什么没有保留

本次尝试做过以下调整：

- 去掉 filler 和无限循环副本。
- 让分页数据按左、右、上、下方向追加。
- 追加时记录视口锚点。
- 通过 `2×2` 优先、`1×1` 补空的顺序减少空洞。
- 对内容边界增加拖动限制。
- 为封面图片增加加载占位和失败回退。

其中 `2×2` 优先只能修复部分固定样例，不能保证多次分页、交替方向和不同卡片尺寸组合下始终没有封闭空洞。继续在这套 first-fit 规则上添加局部条件，会让布局规则与视口边界、分页状态互相耦合，无法形成可靠的不变量。

因此本次按要求撤回这些算法和占位改动，不把未验证的方案作为最终实现。

## 后续重新设计需要满足的约束

重新实现前，需要先明确并测试以下不变量：

1. 每个源模板最多渲染一次，不使用内容复制来填充空白。
2. 已渲染模板的坐标在分页后不能改变。
3. 新页必须落在请求方向的外侧；不能因为分页结果到达而重排旧数据。
4. 布局需要定义「允许的边界空白」和「禁止的内部空洞」，两者不能只用同一个 bounding box 判断。
5. 任意连续分页序列，包括 `right → down → left → up`，都要通过布局测试。
6. 缩放变化不能触发重复加载，也不能让视口停在已加载内容之外的无意义空白处。
7. 虚拟化查询必须只返回真实坐标上的卡片，并与布局索引保持一致。
8. 图片加载状态应与几何布局问题分开验证：加载中、成功、失败分别有明确 UI。
